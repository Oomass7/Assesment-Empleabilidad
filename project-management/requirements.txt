Assessment Técnico — Sistema de Gestión de
Proyectos y Tareas
Java + Spring Boot | Arquitectura Hexagonal

Objetivo
Desarrollar una aplicación en Java 17+ con Spring Boot 3 que permita
gestionar proyectos y tareas, aplicando:
• Clean Architecture (Domain, Application, Infrastructure,
Presentation)
• Enfoque Hexagonal (Ports & Adapters)
• Persistencia en base de datos relacional
• Pruebas unitarias automatizadas
• Frontend funcional
• Docker y Docker Compose
El objetivo es evaluar la capacidad del desarrollador para construir una
solución profesional, enfocada en reglas de negocio, arquitectura y
empleabilidad real.

Autenticación y Seguridad Avanzada
Stack
• Spring Security + JWT (access token)
Endpoints
• POST /api/auth/register
• POST /api/auth/login
Reglas de Seguridad
• Endpoints de escritura requieren JWT válido
• Un usuario solo puede modificar sus propios proyectos y tareas
• Accesos indebidos deben retornar 403 Forbidden
• Manejo correcto de 401 Unauthorized y 403 Forbidden

Arquitectura — Clean Architecture (Hexagonal)
La solución debe implementar Clean Architecture con enfoque
Hexagonal (Ports & Adapters).
Reglas obligatorias
• El dominio no depende de Spring, JPA ni frameworks
• Las dependencias apuntan siempre hacia el dominio
• Los casos de uso representan acciones del negocio
• Controllers, JPA y seguridad son adaptadores
• No debe existir lógica de negocio en controllers

Reglas de Negocio
1. Un proyecto solo puede activarse si tiene al menos una tarea activa
2. Solo el propietario puede modificar un proyecto o sus tareas
3. Una tarea completada no puede modificarse
4. Todas las eliminaciones son lógicas (soft delete)
5. La activación de proyectos y la finalización de tareas deben generar
auditoría
6. La activación de proyectos y la finalización de tareas deben generar
notificación

Pruebas Unitarias Automatizadas
Se deben implementar al menos 5 pruebas unitarias automatizadas
usando:
• JUnit 5
• Mockito
Pruebas mínimas requeridas
• ActivateProject_WithTasks_ShouldSucceed
• ActivateProject_WithoutTasks_ShouldFail
• ActivateProject_ByNonOwner_ShouldFail
• CompleteTask_AlreadyCompleted_ShouldFail
• CompleteTask_ShouldGenerateAuditAndNotification
Alcance
•

Las pruebas deben enfocarse en los casos de uso críticos del negocio

•

No se espera cobertura total de todos los casos de uso

Ubicación y Enfoque
Las pruebas deben ubicarse en la capa de aplicación. Las clases bajo prueba
deben ser:
5

• ActivateProjectUseCase
• CompleteTaskUseCase
• No se deben probar controllers ni adaptadores de infraestructura

Condiciones
• Las pruebas deben ejecutarse sin levantar el contexto de Spring
• Todos los puertos de salida deben ser mockeados
